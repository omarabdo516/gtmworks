# Tests: what each file guards

Every file under `tests/` has a row below (#69): the product promise it guards, how long it runs, the other test that
also guards that promise, and the decision. A test is removed or merged only when another test already proves its
promise, when it checks only implementation detail or wording nobody depends on, or when it re-proves a step every other
test walks through. The first-run setup link (#50), the release install and update (decision 0015), contrast, and the
English/Arabic direction checks are never removed.

## How CI runs them

As Hermes and T3 Code run their CI (#76): a first job decides what runs, the fast layers run on every pull request, and
the whole-app browser and install suites run only when their own area changed, on `main`, or when asked for by hand.
`integration` runs on the runner the repo variable `CI_RUNNER` names, Omar's PC while ci-router keeps it there (#224);
a pull request from a fork runs it on `ubuntu-latest`, where every other job runs. The one PC runner takes one job at a
time, and `database` and `install` take as long or longer there, so they stay on `ubuntu-latest` instead of queueing
`integration` behind them. The compared screens run in their own `visual` job on `ubuntu-latest`, where their approved
images are made, followed by the measured navigation budgets, which need a machine no other job shares (the PC also
runs other repositories' CI); `ci.sh integration` leaves both projects empty (`GTMWORKS_HOSTED_ELSEWHERE`). The compared
screens, the measured budgets and the visual lane run on a push to `main` and on a manual run only, never on a pull
request, and `check` does not wait for them (Omar, 2026-11-17, #257). When they fail on `main`, the `visual` job opens
or updates one issue labelled `visual-regression` that names each failed screen and links the difference images
(`scripts/visual-regression.mjs`); no pull request is blocked by it. A job that
starts the local Supabase stack first reserves its ports on a GitHub-hosted runner (#225). On the PC the ports move to a
block of their own, and `scripts/ci-runner.mjs cleanup` removes what this repository's runs start, before and after.

- `changes` decides which suites a change needs (`scripts/ci-areas.mjs`, like Hermes `detect` and T3 Code `Changes`).
  A change to the CI definition itself (`ci.yml`, `ci.sh`, the area, verdict and runner scripts) or to `package.json`
  and its lock runs every suite; an empty, malformed or unreadable change list runs every suite; a push to `main` runs
  every suite unless every changed file is a document.
- `static` runs on every change: the `node --test` files, lint, types, the unused-code check (`knip`, `knip.json`, as T3
  Code runs it, #81), the catalogue and OpenAPI checks.
  `component-imports.test.mjs` fails there in seconds when a component test's imports reach `server-only` (#218).
- `components` tests screens as components in headless Chromium (Vitest browser mode, `vitest.config.mts`,
  `tests/components/`), in two shards, as T3 Code does (#81). It runs when `app/`, `components/`, `lib/` or the
  component tests change, and when a file the motion test reads changes: the motion table and its reader, the compared
  widths and languages (`tests/visual-screens.mjs`), the reference and `postcss.config.mjs` (#127).
- `database` runs the migration verifications, `check-rls.sql` and `tests/db.sh` (RLS, grants, migrations replayed on
  legacy data) on one local stack, when `supabase/` or a database test file changes. The verifications run in one psql
  session, each file in its own connection and read-only transaction and reported by name (`scripts/verify-db-session.mjs`);
  a verify file is one statement with no psql command, and a canary file checks on every run that the session fails a
  failing file. The migration replays run in one pgTAP session, each with its own ledger line (#259).
- Every lane's stack starts the services `supabase/config.toml` enables, lane 0 and the local stack
  (`scripts/local-db.sh`) included: Studio, analytics (the log services) and the edge runtime are off, as nothing uses
  them. To open Studio on your own machine, set its `enabled` back to `true` locally; do not commit it.
- The stacks' Supabase images come from one archive in the Actions cache, keyed by the Supabase CLI's version and the
  lines of `supabase/config.toml` that choose images (`scripts/supabase-images.sh`). The `supabase-images` job runs
  first: with the key cached it only looks it up, and after a key change it alone pulls the images, once, and saves
  them. `database`, `visual` and a GitHub-hosted `integration` wait for it and restore the archive, so a warm cache makes
  no registry call; it never fails a run, and a job that finds no archive pulls for itself. Each job log ends with how
  many images the registry served.
- `integration` is the whole-app browser suite: the production-shaped proxy suite, then the screens, the functional
  journeys, the measured navigation and first run. All of it runs when the journeys' own area changes: a browser spec or
  its helpers, the fake engines, the Playwright configs, the stacks it runs on (migrations, stack configuration, local
  default privileges, the first-run reset helpers, the image the proxy suite runs in), the seed, `public/`, and the code
  the journeys drive that no component test covers. That code is the server code under `app/` (its `.ts` route handlers
  and server actions, where the server checks permissions), `lib/` outside the catalogues, `worker/` and the root files
  the build and server read. Screens alone (the rest of `app/`, `components/`, the catalogues in `lib/messages/`, the compared
  screens in `tests/visual-screens/` and their approved images) start no browser job on a pull request (#257). Its suite runs on `GTMWORKS_TEST_LANES`
  lanes (four on a GitHub-hosted runner, as many as its CPUs and memory carry on the PC), one per Playwright worker:
  each lane is a whole local Supabase stack and an app server of its own (`tests/lane.mjs`, `scripts/local-db.sh`,
  `scripts/web.sh`), so spec files run side by side and never share data.
  Each functional spec file starts from the seed (`tests/fresh-seed.ts`); tests inside one file still run in order.
  The screens run first, on the seed as built; the navigation time budgets (project `measured`) run after every
  functional test with the machine to themselves, and first run last.
- `lane` is the small visual lane (#257): the key screens in `tests/visual-lane/screens.json` (at most 15), each in
  Arabic at 1440 and 390 in the light and dark themes, compared byte for byte with `tests/visual-lane/images/`. One
  browser pinned by digest (`tests/visual-lane/renderer`) draws them in its container through Playwright's own server,
  so every machine makes the same bytes; the tests, the app and lane 0's stack stay on the runner
  (`playwright.lane.config.ts`). Before each comparison the guards (`tests/visual-lane-guards.ts`) refuse a font that
  did not load, a clock that is not fixed and a request off the machine. It runs on `main` and on a manual run, like
  `visual`. When a picture changes on purpose, one command refreshes the images: `./ci.sh lane-update` (Docker needed;
  without it, `Visual baselines` uploads them as `lane-baselines`). On a manual run, `lane-proof` draws the lane three
  times on `ubuntu-latest` and on the `CI_RUNNER` runner; `lane-proof-compare` fails unless all six sets of hashes match.
- Design parity is checked once, at delivery, outside CI (Omar, 2026-11-17, #257). The worker that delivers a screen
  compares it with its design in `design/` in T3's preview, motions included, at the widths and in the languages the
  design shows, and attaches the evidence (side-by-side images, and a recording for each motion) to the pull request
  that delivers it. No CI job compares a screen with `design/`, and no animation frame is sampled in CI.
- `install` is the Docker install, update, backup, restore, release and one-line install. It runs when the image, its
  build inputs, the install and release files, the migrations it applies or its own checks change, and when `lib/`
  outside the catalogues, `worker/`, `next.config.mjs` or `server.js` change: only the install drives that code against
  the real bundled Hermes.
- A manual run (`gh workflow run ci.yml --ref <branch>`) runs static and the database; the browser suite and the install
  run only with `-f e2e=true` and `-f install=true`, both off by default (like Hermes `e2e` and `e2e_upgrade`).
- `check` is the one required check (like Hermes `all-checks-pass`): a suite `changes` did not ask for passes only when
  it was skipped; one it asked for must succeed; a failed or cancelled stage is red (`scripts/ci-verdict.mjs`).
- `ledger` runs after every stage, also when one failed, and decides nothing (`check` does not need it): it reads the
  results each stage wrote under `ci-ledger/` and the run's jobs from the API, writes `ledger.jsonl` (one record for
  the run, each job and each test, kept 90 days) and puts the layer table in the job summary: result, duration and
  budget (reported, never enforced), queue, runner, test counts, why a layer was skipped and the label of a red job
  (`scripts/ci-ledger.mjs`, `scripts/ci-classify.mjs`, #256).
- The nightly `CI health` workflow (`ci-health.yml`, `scripts/ci-health.mjs`) reads the last 7 days of ledgers and
  replaces the body of one tracking issue, `CI health report`: each layer's p50 and p90, the slowest tests, flaky and
  failed tests, red jobs by label and the PC queue. A change to it runs it on its own pull request.

A pull request that changes only screens runs static, the component tests and the compared screens (#213). A failed
comparison still uploads its expected, actual and difference images in `route-screenshots`. A change to the journeys'
area runs the whole browser suite, and `lib/` outside the catalogues and `worker/` also run the install. Screens alone
get their journeys and install proof on `main`, where every push runs every suite unless every file is a document.

The tests that guard money, sign-in, permissions and Company isolation run as follows:

- The node tests in `static` (for example `route-permissions.test.mjs`, `hermes-usage.test.mjs`, `password.test.mjs`)
  run on every change.
- The database tests (row-level security, grants, the migration verifications, `tests/db.sh`) run in `database` when
  `supabase/` or a database test file changes.
- The browser specs (for example `conversations.spec.ts`, `agent-visibility.spec.ts`, `password.spec.ts`,
  `usage.spec.ts`, `proxy/production-shape.spec.ts`) run in `integration` when the journeys' area changes. That area
  includes the server code under `app/` and `lib/` outside the catalogues, where the server checks roles and the caller's
  Company.
- Every push to `main` runs all three, and a manual run with `-f e2e=true` runs the whole browser suite.
