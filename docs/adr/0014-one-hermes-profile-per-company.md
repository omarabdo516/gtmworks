# One Hermes profile per Company, with Agent levels set by the profile's tools

Omar's decisions of 2026-11-13 on #2 and #3 (their "Decision 2026-11-13" sections), and rules e and f of the same day. This supersedes, where they conflict, the consequence of [ADR 0010](0010-hermes-ships-inside-the-gtmworks-install-and-is-the-engine.md) that the companies of one install share the bundled `default` profile, and the rule of [ADR 0011](0011-agents-are-engine-profiles-made-on-the-management-listener.md) that one Agent is one Engine profile, for the bundled Engine. Everything else in ADR 0008 to 0012 still holds.

## Context

Hermes keeps memory, skills, sessions and model sign-in in a profile's home. With every Company on `default`, an Agent could repeat one Company's facts to another Company's people. Omar chose one Hermes inside the install with one profile per Company over a separate operating-system user or container per Company. A team shares its Company's Agents and their memory; another Company on the same install sees none of it. A Company's Agents get marketing tools only.

The pinned release (Hermes v0.23.0) was read for this, not guessed: `PUT /api/config?profile=` deep-merges into a profile's `config.yaml`; `platform_toolsets.api_server` chooses the toolsets of that profile's Runs and `agent.disabled_toolsets` is applied after everything else; `GET /p/<profile>/v1/toolsets` reports what a Run there gets; a profile made without `clone_from` copies nothing from another profile; the sign-in routes take `?profile=`, ChatGPT (`openai-codex`) is a device-code sign-in the management listener can run, and Claude (`anthropic`) is refused there and signs in only with `hermes auth add anthropic` on the command line.

## Decision

- **A profile per Company.** On a self-hosted install the worker makes each Company with an active Owner its own profile in the bundled Engine, named `co-<company id without dashes>` (`company_engine_profile` in the database, `companyProfile` in `lib/agent-levels.mjs`). The driver (`provideProfile` in `lib/hermes.mjs`) makes it with a short soul, gives it the install key as its Run API key, writes its tools, and reads back from its Run API which toolsets a Run gets. The Company is recorded in `company_profiles` only when Hermes reports none of the toolsets that must stay off. The name is reserved for that Company, so a profile already there under it is a create that stopped part way and is finished; a profile is never cloned, so it starts empty.
- **Attaching.** A Company with no Hermes at all gets a Connection to its own profile and its main Agent, Lead, as ADR 0010 did with `default` (`attach_company_profile`). A pasted Connection is never replaced or moved.
- **A Company profile serves one Company.** A Connection naming a Company profile (`co-<id>`) is refused for any other Company, in `hermes_connections` and in `hermes_agents` (triggers, so the Owner-of-two-Companies sharing confirmation cannot pass it), and again when a Run is reserved and before the driver is called (`lib/conversation-runs.mjs`).
- **Runs are reserved before Hermes is called.** The sender's session reserves the Run (`reserve_conversation_run`, with the message), which pins the Agent's Connection under the lock a move takes; the Run starts on that Connection, a retry reserves the same one, and recording the message ends the reservation. A reservation never expires and its Connection cannot be deleted under it. One whose message was never recorded is settled by the worker after two minutes: it starts the Run again on the pinned Connection with the same idempotency key, which replays the Run Hermes started or starts it, and records it as the person's message (`settle_conversation_run`); a message whose start answer was lost is therefore delivered late rather than dropped. A move waits while any reservation or open Run holds one of its Connections, and until no message of the Company's conversations on them was written in the last five minutes. That window covers the previous app version, which calls Hermes before it records and never reserves; the risk left is a message it sends after five quiet minutes, in the instant between its call and its record, while that Company moves: that Run would end as lost.
- **Tool policy and pending changes.** The level table is versioned (`toolPolicy` in `lib/agent-levels.mjs`, `engine_tool_policy()` in the database, the table's fingerprint pinned in a test). A profile records the policy and level its tools were applied under; a profile under another policy is applied again at the same level. Before changing a recorded profile's tools the worker marks them pending (`begin_company_tools`); only the recorded read-back clears the mark, and no Run starts on a profile that is pending, under another policy or at another level.
- **Agents on the Company profile.** All of a Company's Agents on the bundled Engine run on the Company's one profile and share its memory, skills and sign-in, which is the team-sharing Omar asked for. Each Agent keeps its own Connection row (one Agent per Connection, `hermes_agents` unique per Company and Connection), naming the Company's profile; each Conversation is its own Hermes session in that profile. The driver's `createAgent` (a profile per Agent) stays for a pasted Hermes and is not used for the bundled one; an Agent's own instructions are a later ticket and do not get their own profile.
- **Agent levels.** `companies.agent_level` is 1 (read and draft), 2 (act on approval) or 3 (scheduled work); every Company starts at 1. Only an active Owner changes it, through `set_agent_level`, and each change is in the Company's log. The level is enforced by the profile's tools and by gtmworks approvals, never by prompt text. `lib/agent-levels.mjs` holds the one table: level 1 gets web, vision, image generation, skills, a task list, memory and session search; level 3 adds cron jobs. Level 2 gets exactly level 1's tools: gtmworks has no path yet that holds an action until a person approves it, so the level is recorded and shown as acting on approval with no action tools yet (lead's decision on the review of this ADR). terminal, file, code_execution, computer_use, browser, delegation, project, desktop_ui, catalog, onboarding, kanban and Hermes's `connections` (actions in connected accounts) are always in `agent.disabled_toolsets`, with the higher levels' toolsets. The composites `debugging` and `safe` are not listed, because Hermes strips every tool of a disabled composite and they would take web search with them; `coding` is a posture Hermes subtracts only by its non-core tools, so listing it would do nothing. The worker writes the table again when the level changes and reads it back against the requested level's whole deny list; only then does it record the applied level (`company_profiles.tools_level`). Until the applied level equals the requested one, no new Run starts on the profile (`reserve_conversation_run` refuses with `agentLevelPending`), so a downgrade Hermes did not apply never runs with the old tools.
- **Tool health.** Every five minutes the worker reads the toolsets of every connected Connection that an Agent uses, pasted ones included, and records which of terminal, code_execution and file are on (`engine_tool_checks`). `agent_tool_warning` tells a Company's Owner, on Settings, Company, which of its Agents have one while more than one person is a member. A pasted Hermes is only read, never changed. A bundled Company profile the Engine no longer serves (its data was not restored with a backup) is forgotten, and the worker makes it again, empty.
- **Model sign-in (#3).** The sign-in lives in the Company's profile. On Settings, Subscription and models, an Owner starts ChatGPT's sign-in; the page shows Hermes's code and https link and asks Hermes until it is approved, denied or expired, and the Owner can disconnect, which removes the credential from that profile only. Every step is checked on the server (`is_company_owner`); a member sees whether each subscription is connected and has no button. The driver passes on states, the code and the link only, never a credential, token preview or Hermes error text. Claude stays a documented install-command path (lead's decision): the page shows the exact command for the install owner, `hermes -p <profile> auth add anthropic --type oauth --no-browser` run in the `hermes` container, in both languages, because the pinned release refuses to start it from its management listener; its Disconnect works. Hermes lets a profile with no credential of its own use the root `default` profile's, reports it as logged in either way, names no source and has no setting to turn that off (hermes_cli/auth.py, `read_credential_pool`, `_load_provider_state`). So the driver reads the `default` profile too, and a provider signed in there is reported as "Not connected (shared sign-in on the default space)", never as the Company's, with a warning on the page; such a sign-in never moves a Company either.
- **Existing installs.** A Company whose Agents run on a bundled Connection to another profile (the old shared `default`) gets its own profile at once but keeps running where it is. The worker moves it (`move_company_profile`: a new Connection per old one, the Company's Agents re-attached, an old Connection no Agent uses removed) once its own profile holds a model sign-in, so it is never left without a model, and never while one of its Runs is open, because a Run is read on the profile it started on. Its signed-in state is asked at most once a minute.

## Consequences

- Memory already written on `default` stays there; it cannot be split by Company. Conversations moved to a Company profile keep their gtmworks record but not their earlier Hermes context.
- Hermes reads the root `default` profile's OAuth sign-ins for any profile that has none of its own. gtmworks fails closed on this: while `default` holds a sign-in for a provider, no Company shows that provider as connected, even one with its own sign-in, and the README tells the install owner not to sign in on `default`. A model configured on `default` with an API key in its `.env` or `config.yaml` is not read by Company profiles: such an install's Companies stay on `default` until they sign in.
- A new Company's Agents answer only once it has a model: its own sign-in, or a sign-in on `default` as above.
- `install.sh backup` still does not include the `hermes` volume (ADR 0010): after a restore, profiles are made again empty and each Company signs in again.
- Skills and memory stay writable by the Agent inside its own profile at every level (Hermes's `skills` and `memory` toolsets). Lessons proposed through gtmworks still wait for approval.
- The previous app version's `provide_bundled_hermes` is left in place, so its worker may still give a new Company `default` during an update; the new worker then moves it.
- The install job proves on the pinned release that two Companies get two profiles, each with terminal, file and code execution off in its config and absent from its Runs' toolsets, that a Run on each answers, and that a memory written in one Company's profile reaches its Run and never the other's (`scripts/check-install-profiles.mjs`).
- The install job also scans the bundled Hermes's environment and every file its user can read for the real values of gtmworks's secrets from `.env.install` (`scripts/check-hermes-keys.py`, names only in its output), and a unit test fails when the compose file passes one of them to Hermes.
