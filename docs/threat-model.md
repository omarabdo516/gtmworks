# Threat model

What a reviewer should protect in gtmworks, read from the code and the ADRs. Every claim names its source; a control that is planned and not built is marked "planned".

## Entry points and who can call them

- **Browser sessions.** People sign in with Supabase Auth; `middleware.ts` refreshes the session on every route except `/api/health`, `/api/config`, `/api/client-errors` and static files (its `matcher`). Pages and server actions query with the person's session and the anon key, so RLS applies (`lib/supabase.ts`, ADR 0004). Company pages live at `/c/<slug>/...` (ADR 0004).
- **Public, anonymous routes.** `/api/health` (health only), `/api/config` (the public Supabase URL and anon key), `/api/client-errors` (browser errors written to the log, redacted, at most 60 lines a minute: `lib/diagnostics.mjs` `redact`, `limiter`). `POST /first-run/submit` creates the first owner and company with the service key, only while `setup_is_open()` is true and only with the one-time setup code the installer prints in its setup link (`SETUP_CODE` in `.env.install`, 256 bits, compared in constant time: `lib/setup-code.mjs`; the link carries it after `#`, so it reaches the server only in the submit body: `lib/setup-link.mjs`) (`app/first-run/submit/route.ts`, `supabase/migrations/20261126000000_first_run.sql`).
- **Session API routes.** `/api/hermes-agents` and `/api/recent-cards` require a signed-in user (`auth.getUser()`); the Hermes route refuses a POST that is not JSON or whose `Origin` host differs from `Host`. The pasted-Hermes route `/api/hermes-connections` is gone (#342) and answers 404.
- **The Hermes connection (outbound only).** gtmworks calls each Company's Engine (ADR 0018); an Engine does not call gtmworks. The app and the worker take a Company's address and key from its Engine record (`lib/company-engine.mjs`, `lib/engine-record.mjs`, #381); the record is the only source, and the install-wide environment values are gone from the app and worker containers. All calls are in `lib/hermes.mjs` (ADR 0008): bearer key, `redirect:'manual'`, 5 s timeout, and plain HTTP only to loopback, private, CGNAT and `.local`/`.internal`/`.ts.net` hosts (`isHermesAddressAllowed`).

## Trust boundaries

- **Company owners and members.** `is_member(company)` gates reads on every company table; writes follow the member's role (`can_manage_company`, `work_can_edit`, ADR 0004). A company the person is not a member of reads as nothing. No Agency bypass and no two-step requirement exist (ADR 0012, `supabase/migrations/20261204000000_remove_agency.sql`).
- **Company owners only.** `is_company_owner(company)` (an active Owner member) gates managing the Company's agents, the `record_conversation_*` writes, the shared-Engine notice and usage (ADR 0012).
- **Agents.** An Agent is one of its Company's own Agents, an Engine profile, and never a member: the four legacy role agents, their shared identities, company grants and the role key on a membership are removed (spec #695, ADR 0034, `20270418000001_legacy_role_agents_cutover.sql`). An identity that was one of them keeps a removed membership and is banned from signing in, so it reaches no Company's rows. There are no agent or run keys and no `/api/v1` API: both were removed with the external-agent API (#341, `20270206000000_remove_external_agent_api.sql`), and the old routes answer 404.
- **The service role.** Bypasses RLS. Held only by these clients (#778; `tests/audit-defects.test.mjs` fails when a file makes one and is not named here, or is named and makes none): `lib/first-run.ts` (`setupAdmin`: first-run setup in `app/first-run/submit/route.ts`, and `app/first-owner/submit/route.ts`, which claims a first-Owner link and makes that Company with its Owner); `lib/invitation-mail.ts` (sends the invitation email through Auth's admin API, after `invite_member` checked the Owner); `lib/company-engine.mjs` (`serviceDb`, the one client every Engine lookup answers from); `app/api/conversations/route.ts` (a message's send, its Run and its kept files); `app/api/channels/route.ts` (a channel's permission, question, hand and stop answers, each sent on to the Engine); `app/api/run-steps/route.ts` (reads the Engine record for a Run's steps); `app/api/dictation/route.ts` (reads a Company's Agent profile and record for a transcript); `app/api/provider-keys/route.ts` and `app/settings-overlay.tsx` (a Company's provider keys, written to and read from its Engine); `app/channel-archive-actions.ts` (stops a channel's Runs as it is archived); `app/c/[slug]/[[...section]]/work-actions.ts` (starts a note's Run); `app/c/[slug]/chat/[[...agent]]/page.tsx` and `app/c/[slug]/conversations/[id]/page.tsx` (the main Agent's opening, written once on the Owner's first visit); the worker (`worker/index.mjs`, the Runs of Conversations and channels); and the installer's own scripts run inside the web container (`scripts/install-engine.mjs` registers or adopts each Company's Engine record; `scripts/company-add.mjs`, `scripts/company-list.mjs` make a Company with its Owner and report each Engine). Each one is reached only after the signed-in person's own client checked the Role or the record (except setup, the first-Owner link and the worker). Elevated functions are granted to `service_role` only (`lookup_agent_key`, `agent_rate_limit`, `claim_webhook_deliveries`, `issue_run_key_for`, `setup_is_open`, `complete_setup`, `attach_engine`, `adopt_engine`, `create_company_with_owner`, `claim_company_owner_link`).
- **Isolation tests.** `supabase/tests/foundation.sql` fails when a public table lacks RLS; `supabase/shared-tables.txt` lists the tables without a company column. The install job proves Company isolation on the pinned Engine (#126): two Companies with a main Agent and a second Agent each, every Agent on its own profile and every Company on its one shared space; terminal, file and code tools off in every Agent profile's config and absent from its Run API; a Run on a shared space refused; a memory written in one Company's main Agent reaching that Agent's Run only; a Skill in one Company's shared folder listed for its two Agents and for neither of the other Company's; a key set for one Company set in its own profiles and never in the other's or the root; and the database refusing a `hermes_agents` row of one Company that names the other's profile. `scripts/check-install-profiles.mjs` prints names and states only (`lib/install-proof.mjs`), and `scripts/check-hermes-keys.py` scans every Engine's files, every profile included, and once more after the twenty profile-size profiles (`install-measure`, on `main` and a manual run). The install job also runs `scripts/check-install-engine-network.mjs` from the first Engine's own network: the database, auth, REST, storage and the gateway are unreachable there, and the app answers a forged visitor address exactly as it answers the internet; it inspects every container for a Docker socket mount (#381).

## The work sandbox and its exit

Every Member who talks to an Agent, and every page an Agent reads, is assumed able to run any command in that Company's work sandbox (ADR 0018, spec #389). The boundary is what that command can reach.

- **The sandbox.** One container per Company, beside its Engine, made from the Company's template (`scripts/engine-template.yml`) by the installer and by `gtmworks company add`. Every Agent's terminal, files and code run there over the Engine's `ssh` backend, pinned in the Engine's managed configuration (`scripts/engine-managed.yml`); the sandbox accepts that Engine's key and no password (`sandbox/sshd_config`). It runs as the image's ordinary user (uid 1000) with no capability, no new privilege, a process limit and its Company's memory and CPU limits; what lasts is the Company's work folder, one volume. No container of the install mounts the Docker socket (#393).
- **Its network.** The sandbox is on one network of its own, `internal` (no route out), shared only with its Engine and its exit. The Engine binds its Run API and management listener to its install-network address only, so they do not answer on the work network (`scripts/engine-listener-address.py`, #390). The app, the worker, the database, auth, REST, storage, the gateway, another Company's Engine and another Company's sandbox are on no network the sandbox joins.
- **The exit.** One per Company, in the same template, so making a Company changes nothing shared (#394). It is a small HTTP proxy (`sandbox/exit.py`) run from the work sandbox image, so an install loads, pins and updates no second image; it runs as the same ordinary user with no capability, no volume of the install and no port, it is the only container on the work network with a second network that routes out, and it listens on the work network alone. The sandbox's environment and every `ssh` session point HTTP and HTTPS at it (`HTTP_PROXY`/`HTTPS_PROXY`, `sandbox/Dockerfile`, `sandbox/sshd_config`). It forwards a plain HTTP request to port 80 after rebuilding its head (a request pipelined after it on the same connection goes to the same checked address), and opens an HTTPS tunnel (CONNECT) to port 443 only when the client's first bytes are the header of a TLS ClientHello record. It refuses every other port, and it refuses by the address a name resolves to, checking every address and connecting to the exact address it checked, so a name that answers differently a second time (DNS rebinding) changes nothing: private (RFC 1918, ULA), shared (RFC 6598), loopback, link-local, cloud metadata (169.254.169.254, fd00:ec2::254, the one in the shared range and Azure's WireServer, 168.63.129.16), multicast and reserved ranges, an IPv4 address written as IPv6 (mapped, compatible or SIIT-translated) or inside a tunnel or translation prefix, and the networks the exit itself is attached to. The install's own networks are Docker networks in private ranges, so they are refused by address as well as unrouted.
- **What cannot be reached from the sandbox.** Proved from inside a real sandbox, over the Engine's own `ssh` login, by the install job (`scripts/check-install-sandbox-exit.mjs`, in the `first-install` and `companies` areas): every install service by name and address, the app and the worker, the Engine's listeners on both its addresses, and another Company's sandbox, Engine and exit, directly and through the exit; private, shared, link-local, loopback and metadata addresses through the exit, by number and by a name that resolves to them; and, directly, any port of a public host, a datagram and a DNS name of the internet, and through the exit any port but 80 and 443, high ones too, and a tunnel that is not TLS, even behind TLS-looking first bytes. A stand-in public host outside the install's networks answers through the exit over HTTP and HTTPS, from the shell and from Chromium. `tests/sandbox-exit.test.mjs` runs the exit's rules on their own.
- **No keys.** The sandbox's and the exit's environment and files hold none of gtmworks's secrets, not their Engine's API key, not the private key the Engine dials the sandbox with, and no model credential: `scripts/check-hermes-keys.py` scans both for those values (the `agents` area). A paid service is called by a tool of the Engine, never from the shell.
- **What remains.** The sandbox shares the server's kernel: a kernel escape from a container is an escape from the sandbox (a stronger runtime such as gVisor is out of scope). Every Agent of a Company shares one sandbox, so one Agent's files and running processes are visible to, and changeable by, the others; nothing in it is private to an Agent. HTTP to port 80 and HTTPS to port 443 of any public address leave, and no other port: a page or a command can send what the sandbox holds (the Company's work folder) to any public site. The server's own public address is reached through the exit as the server itself reaches it, from inside, so a provider's firewall in front of the server does not stand between them: ports 80 and 443 of it are reachable from the sandbox, and so is any service of the operator's own that listens there on 80 or 443. Disk is not limited per Company: a sandbox's work folder and its own writable layer sit on the Docker host's disk with the database, Storage and every other Company's volumes, so commands that write until the disk is full stop the whole install. Memory, CPU and processes are capped; a byte or inode quota per Company is not (#507). The ranges reserved for documentation are not refused, since they route nowhere; the install proof's stand-in host uses one. An install whose Docker address pools are set to public ranges has only the networks the exit is on refused by address; the rest stay unrouted.

## Secrets and privileged actions

- **Settings.** `.env.install` holds every install value; each Engine's own key is in its own `.engines/<name>/.env` (`lib/install-env.mjs` makes it; #385). The web app and the worker get only the values they read, each named in `docker-compose.install.yml` (`CONTAINER_ENV` in `lib/install-env.mjs`, #446): `SUPABASE_SERVICE_ROLE_KEY`, `WEBHOOK_ENCRYPTION_KEY`, the public key and addresses, and for the app the setup code. `POSTGRES_PASSWORD`, `PGSODIUM_ROOT_KEY` and `SUPABASE_JWT_SECRET` reach only the installer and the database, auth, REST and storage containers, and the app and worker refuse to start holding one (`validate web|worker`). A break-in into the app cannot sign in to the database as `postgres` or sign a JWT itself, but it still holds the service-role key: every table past row-level policy, and Auth's admin API (`auth.admin`, which first run uses), through which it can set any person's password or make a sign-in link and so take over any account.
- **Engine key.** Each Engine's key is install-generated and kept in that Engine's own file, never in the app's or the worker's environment file; the installer passes it only to the Engine record registration (`scripts/install-engine.mjs`) and the checks. Every call reaches an Engine through its Company's record, which holds the key encrypted with the install's encryption key (#380, ADR 0018); since #342 no Hermes key is stored in any other table (the encrypted Connection keys went with `hermes_connections`). No route returns it and no log line names it.
- **Logs.** `lib/diagnostics.mjs` keeps only the company id and slug from a form and redacts secret settings, bearer tokens, long tokens and 6-8 digit codes. A new `console.*` call bypasses it.
- **Privileged actions.** First-run setup; inviting members (the Owner's `invite_member`, then the email by the service key); approving a version (a person only).

## Look here first

1. **Every service-role call site listed above.** A new one, or one without a filter on owner, company or id, skips RLS for everyone.
2. **Anything that receives or sends a key**: `lib/hermes.mjs`, `lib/company-engine.mjs`, the provider-key route. Look for a key, header, request body or remote error text in a log, a response or a stored error, and for a redirect followed with a key.

Planned, not built (never treat as enforced): fenced leases, heartbeats and a watchdog for runs (ADR 0006, superseded by ADR 0034); conversations relayed from Hermes (#190, ADR 0008).
