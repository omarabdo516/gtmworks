# Checks and CI layout

`./ci.sh check` runs `./ci.sh fast` (the static checks, the node tests and the component tests at once; `./ci.sh static` leaves out the component tests), `./ci.sh database`, `./ci.sh visual` then `./ci.sh integration`; CI also checks the Docker install with `scripts/ci-install-check.sh`, which `./ci.sh install [area]` runs here on an isolated Docker machine. Each file under `tests/` keeps its row beside it in `tests/rows/`, and `node scripts/testing-doc.mjs --print` prints those rows as a table (`./ci.sh static` fails when a test file has no row or a row names no file). In CI every job runs on a GitHub-hosted `ubuntu-latest` runner (decision 0038, #334); the visual lane and the measured navigation budgets run in their own `visual` job, where no other job shares the machine. They run on a push to `main` and on a manual run only, never on a pull request, and `check` does not wait for them; a failure on `main` opens or updates the `visual-regression` issue (Omar, 2026-11-17, #257). The chat's open time runs in its own `chat-open` job, with a machine to itself, on a pull request too (#421): the browser shards leave it empty. The profile-size measurement runs the same way (#408). Design parity is checked once at delivery, outside CI (`docs/testing.md`).
## What runs when

In CI the first job decides what runs (`scripts/ci-areas.mjs`, as Hermes and T3 Code do, #76): the `fast` job runs on every change, its steps at once with each result listed in `check` (#258), and its screen component tests (Vitest in headless Chromium, one run) run when `app/`, `components/`, `lib/` or their tests change; the database tests, the whole-app browser suite (`integration`) and the install run on a pull request only when their own files change (`docs/testing.md` lists them); a draft pull request runs what a ready one runs, so those suites start on a draft too and `check` waits for them, while marking a draft ready starts nothing by itself (#405). The install proof is one `install` job with one matrix entry per area, each on a fresh isolated Docker machine of its own, named for the area and run by one command of the repo: `install-first-install` (`./ci.sh install first-install`, the first install and its repeat), `install-companies` (`./ci.sh install companies`, Companies and their Engines, #407), `install-agents` (`./ci.sh install agents`, Agents on their Engines, #408), `install-backup` (`./ci.sh install backup`, backup and restore, #409), `install-proxy` (`./ci.sh install proxy`, the public address behind a proxy), `install-rollback` (`./ci.sh install rollback`, a failed update rolled back, #389), `install-update` (`./ci.sh install update`, the update between releases), `install-previous-archive` (`./ci.sh install previous-archive`, the previous release's own archive restored, split from the update area by #389), `install-sandbox-update` (`./ci.sh install sandbox-update`, `./ci.sh install staged-update`, an install the release before the work sandbox made, with two Companies, updated to this one, #397), `install-staged-update` (`./ci.sh install staged-update`, the staged removal of Agent levels: updates that fail after the first step leave the previous release serving, and the cutover follows only once this release answers, ADR 0023), `install-sizes` (`./ci.sh install sizes`, the measured sizes the README states and the default sandbox limits a render finishes within, #400), `install-engines-update` (`./ci.sh install engines-update`, a release that pins another Engine image, #389), `install-one-line` (`./ci.sh install one-line`, the one-line install) and `install-updater` (`./ci.sh install updater`, Update now's updater, #443); a new area is one more matrix entry (#406). The profile-size measurement is a job of its own, `install-measure` (`./ci.sh install measure`), on a push to `main` and on a manual run only, which `check` does not wait for (#408). The app image is built once per run, by its own `image` job, which runs when the browser suite or the install proof is asked for, and on every manual run, where the measurement runs; `integration`, the install proof and the measurement load that build and build nothing of their own, and `check` waits for the image job and is red when it failed or was cancelled (#403, #406, #408). The image build passes `NEXT_SKIP_CHECKS=true`, so `next build` repeats no lint and no type check `fast` already ran; a release image and a local build keep both. A change to the CI definition or `package.json` runs all; unknown or empty diffs run all. Screens alone run the fast job, its component tests included (#257). The browser suite runs as six shards, and their browser comes from the cache the fast job keeps, keyed by Playwright's version and the runner image, so no shard downloads a browser, a system package or a font during a run (#404). Screens are `app/` outside its `.ts` server code, `components/`, the catalogues in `lib/messages/`, and the visual lane's screens and images. A component test alone runs only the fast job. The journeys, the measured navigation, first run, the proxy suite and the image run when the journeys' own area changes: a browser spec or its helpers, the fake engines, the Playwright configs, server code under `app/` (its `.ts` route handlers and server actions), `lib/` outside the catalogues, `worker/`, the server and build files, the migrations, the seed, the image or `public/`. A push to `main` runs every suite unless every changed file is under `design/`, under `docs/`, or ends in `.md` (files under `public/` excepted), judged against the last commit a successful main CI run tested. A manual run starts the browser suite and the install only with `-f e2e=true` / `-f install=true`, off by default. `check` passes a suite nobody asked for only when it was skipped.

Every job of the full check — `changes`, `fast`, `supabase-images`, `image`, `database`, `integration`, `chat-open`, `install` and `check` — has a time limit near its budget: one and a half times the minutes measured on run 44636876755, the first run with every other ticket of spec #401, kept between 3 and 12 minutes; `chat-open` is new in #421 and its first run confirms the 5 minutes estimated here. `visual` and `install-measure` are no part of the full check and keep the limits they had. A job that runs past its limit ends as cancelled or failed, and `check` is red either way. `tests/ci-budgets.test.mjs` reads the limits from `.github/workflows/ci.yml` and fails when one rises without this table changing:

| Job | Measured | Limit |
|---|---|---|
| `changes` | 0.2 min | 3 min |
| `fast` | 2.7 min | 5 min |
| `supabase-images` | 0.1 min | 3 min |
| `image` | 3.4 min, with the work sandbox image (run 44726291691) | 6 min |
| `database` | 2.1 min | 4 min |
| `integration` | 10.6 min, its slowest shard | 12 min |
| `chat-open` | 5 min, an estimate until its first run | 8 min |
| `install` | 10.7 min, its slowest area (update, run 44726291691) | 12 min |
| `check` | 0.1 min | 3 min |

CI deploys nothing. An install picks up a merge when its owner runs `sh scripts/install.sh update` (README), which applies new migrations before the new app version starts; a failed migration rolls back and the previous app keeps serving. A later version does not undo an applied migration; recovery needs a new forward migration. A forward migration cannot bring back deleted data; restore it from a backup.

## Running the install proof by hand

`./ci.sh install [area]` runs the whole install proof — `scripts/ci-install-check.sh` — or one area of it, on the machine you are on, so an agent or a reviewer sees the real error text without a push. Without an area the fourteen areas (spec #401's seven, #389's rollback, previous-archive, engines-update and staged-update, #397's sandbox-update, #400's sizes, and #443's updater) run one after another, then the profile-size measurement: the first install and its repeat; Companies and their Engines; Agents on their Engines; backup and restore; the public address behind a proxy; a failed update rolled back (`./ci.sh install rollback`, split from the update area by #389 to keep it within 12 minutes); the update between releases (`./ci.sh install update`); the previous release's own archive restored onto this release (`./ci.sh install previous-archive`, split from the update area by #389 when the work sandbox took it past its 12 minutes); an install the release before the work sandbox made (a fixed commit of `main`, an Engine per Company and no sandbox) with two Companies, an Agent's memory and a level change, updated to this release: a failed update first, which leaves that release serving with no sandbox made, and one whose sandbox image cannot be pulled, which applies no migration, then the update, after which each Company has its own sandbox, exit and work folder, its Engines are pinned to it with no file sync, an Agent made before it runs a command in its sandbox and remembers, the file it made in its old Library is in its own folder and its Library, the level is gone and its change still reads in the log, and the install command again keeps each sandbox and its work folder and copies no old file over a changed one (`./ci.sh install sandbox-update`, `./ci.sh install staged-update`, #397), the staged removal of Agent levels with updates that fail after its first step (`./ci.sh install staged-update`, ADR 0023); the measured sizes (`./ci.sh install sizes`, #400: the idle memory of the install, an Engine and a sandbox, one short render at the default sandbox limits, and a render stopped at a low limit while the other Company's sandbox answers); a release that pins another Engine image (`./ci.sh install engines-update`); the one-line install; and Update now's updater (#443). Every area is independent and starts from a fresh install, so the order changes no result; in a full run each area runs in a subshell of its own, so one area's failure sentence, EXIT trap, `HOME` or current folder cannot reach the next (#411). With an area only it runs, on a fresh isolated Docker machine: `./ci.sh install first-install` (the first install and its repeat), `./ci.sh install companies` (#407), `./ci.sh install agents` (#408), `./ci.sh install backup` (#409), `./ci.sh install proxy`, `./ci.sh install rollback`, `./ci.sh install update`, `./ci.sh install previous-archive`, `./ci.sh install sandbox-update`, `./ci.sh install staged-update`, `./ci.sh install sizes`, `./ci.sh install engines-update`, `./ci.sh install one-line`, `./ci.sh install updater` (#443) and `./ci.sh install measure` (#408) each make the install, its first run, the Companies, the archives, the registry and the release files they need themselves (#406–#409). It needs a working Docker daemon: without one it stops before starting anything and prints one line, `the install proof needs Docker: docker info cannot reach a daemon`. It runs `HEAD` in a throwaway checkout under the git directory (commit first; uncommitted changes are not run), starts `gtmworks-install-lane`, a `docker:28.5.1-dind` container of its own, loads the images the proof runs from this host's Docker (the machine's nested network cannot pull), and removes the container and the checkout when it ends, also after a failure. It stops at its first failed check and prints the sentence that check names: `install check failed: …` for the install areas, `release install check failed: …` for the update between releases, and `one-line install check failed: …` for the one-line install. CI runs the same file, once per area (`bash scripts/ci-install-check.sh first-install`, `… companies`, `… agents`, `… backup`, `… proxy`, `… rollback`, `… update`, `… previous-archive`, `… sandbox-update`, `… staged-update`, `… sizes`, `… engines-update`, `… one-line`, `… updater`), as one `install` job's matrix, one entry per area named for it, each on its own isolated Docker machine, and the measurement as the `install-measure` job (`… measure`); the machine and the run's image are one composite action, `.github/actions/install-machine`, used by both, and the image is loaded under the tag `docker-compose.install.yml`'s `web` service names, read from that file (#411), so no job builds it: CI sets `GTMWORKS_IMAGE_PREBUILT=true`, which `scripts/install.sh` reads only to skip `compose build web` and say so in one line (tests only). The helpers the areas share live once in `scripts/ci-install-lib.sh` (#402, #406), among them each area's start (`area_setup`: its failure sentence and EXIT trap), the first Engine's node checks and file values, the second Company and the app image's tag (#411).
