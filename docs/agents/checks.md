# Checks and CI layout

`./ci.sh check` runs `./ci.sh fast` (the static checks, the node tests and the component tests at once; `./ci.sh static` leaves out the component tests), `./ci.sh database`, `./ci.sh visual` then `./ci.sh integration`; CI also checks the Docker install. Each file under `tests/` keeps its row beside it in `tests/rows/`, and `node scripts/testing-doc.mjs --print` prints those rows as a table (`./ci.sh static` fails when a test file has no row or a row names no file). In CI every job runs on a GitHub-hosted `ubuntu-latest` runner (decision 0038, #334); the visual lane and the measured navigation budgets run in their own `visual` job, where no other job shares the machine. They run on a push to `main` and on a manual run only, never on a pull request, and `check` does not wait for them; a failure on `main` opens or updates the `visual-regression` issue (Omar, 2026-11-17, #257). Design parity is checked once at delivery, outside CI (`docs/testing.md`).
In CI the first job decides what runs (`scripts/ci-areas.mjs`, as Hermes and T3 Code do, #76): the `fast` job runs on every change, its steps at once with each result listed in `check` (#258), and its screen component tests (Vitest in headless Chromium, one run) run when `app/`, `components/`, `lib/` or their tests change; the database tests, the whole-app browser suite (`integration`) and the install run on a pull request only when their own files change (`docs/testing.md` lists them); a draft pull request runs what a ready one runs, so those suites start on a draft too and `check` waits for them, while marking a draft ready starts nothing by itself (#405). A change to the CI definition or `package.json` runs all; unknown or empty diffs run all. Screens alone run the fast job, its component tests included (#257). Screens are `app/` outside its `.ts` server code, `components/`, the catalogues in `lib/messages/`, and the visual lane's screens and images. A component test alone runs only the fast job. The journeys, the measured navigation, first run, the proxy suite and the image run when the journeys' own area changes: a browser spec or its helpers, the fake engines, the Playwright configs, server code under `app/` (its `.ts` route handlers and server actions), `lib/` outside the catalogues, `worker/`, the server and build files, the migrations, the seed, the image or `public/`. A push to `main` runs every suite unless every changed file is under `design/`, under `docs/`, or ends in `.md` (files under `public/` excepted), judged against the last commit a successful main CI run tested. A manual run starts the browser suite and the install only with `-f e2e=true` / `-f install=true`, off by default. `check` passes a suite nobody asked for only when it was skipped.

CI deploys nothing. An install picks up a merge when its owner runs `sh scripts/install.sh update` (README), which applies new migrations before the new app version starts; a failed migration rolls back and the previous app keeps serving. A later version does not undo an applied migration; recovery needs a new forward migration. A forward migration cannot bring back deleted data; restore it from a backup.
